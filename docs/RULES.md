# The rulebook

Every decision a mesh run makes on its own is made by a written rule. Each rule has a stable ID,
and each decision the run records in its "why" record names the rule behind it
(`contracts/decision_record.py`). This file is the one home for those rules.

Rulebook version: **94**

How the book is kept honest:

- A rule's ID never changes and is never reused. A rule that stops applying is marked `retired`,
  not deleted.
- **In force** means the code makes this decision today. **Planned** means the ID is reserved
  for a later PR (named in brackets) and no code may cite it yet.
- `tests/unit/hygiene/test_rulebook.py` checks, on every PR, that every rule ID the code cites is
  in force here, that every in-force rule here is cited by the code, and that the version above
  matches `RULES_VERSION` in `contracts/decision_record.py`.
- Changing what a rule decides means changing this book in the same PR and raising the version.

Each decision in the record also says where it came from:

| Source | Meaning |
|---|---|
| `rule` | The code decided by the rule, from measured or declared facts. |
| `user` | The user decided (named an engine, or confirmed one). The rule says why that stands. |
| `ai-lever` | The AI made a judgement call from a declared list (the FEA builder's AI-fea-n), and the rules made it exact inside their limits. |
| `guard-clock` | A guard clock tripped (TIME-3), or one of the clocks still left for the CAD repair work decided (TIME-6). Since D3 no other clock decides anything. |

## ENG: which engine meshes the run

| ID | Status | Rule |
|---|---|---|
| ENG-1 | in force | **Only engines that can take the case are ranked.** An engine is a candidate only if its declared capability covers the flow, the file's form, the number of separate passages and the layers asked for. |
| ENG-2 | in force | **Home turf first.** An engine that declares the measured shape class its home (`EngineSpec.home_classes`: VMTK for tubes and branching passages) comes first, unless its own turf rows mark the case a weak spot or outside. Two home engines rank between themselves by ENG-4. |
| ENG-3 | in force | **The lab record overrides home turf only when it clearly wins:** the challenger has at least 20 runs on at least 8 different shapes of this class, no quality fault, and a 95% lower bound above the home engine's 95% upper bound. A home engine whose own record of 20+ runs here shows a quality fault also loses first place. A home engine never tried on the class keeps it ("home turf unproven"). |
| ENG-4 | in force | **The best lab record on shapes like this one comes first.** The run's geometry is measured, and engines are ranked by the Wilson 95% lower bound of their pass rate on its shape class (`engines/fitness.py`), each run short of 20 counted as a miss, so 7 of 8 never beats 14 of 19. The table is dev-side runs only, versioned (`docs/engines/fitness-changelog.md`). An engine with a quality fault ranks after the sound ones; an engine whose declared turf puts the shape outside is never recommended. Ties go to fewer broken meshes, then fewer bad cells, then the declared turf, layers and ladder order. Time never breaks a tie. |
| ENG-5 | in force | **The fallback ladder walks the same ranking**, after the approved engine, minus the engines already tried and the engines that would refuse the case. With nothing measured, the same rules rank the engines on their record over the whole flow, never a fixed order. |
| ENG-6 | in force | **The user's pick stands.** An engine the user named is never switched on its own; another engine is only offered. A dispute keeps the engine of the mesh it disputes. |
| ENG-7 | in force | **An engine that reads the upload's own format comes first**, measured or not: a conversion loses what the file describes (an ECXML's parts, materials and powers). |
| ENG-8 | in force | **Nothing measured, nothing named: the declared default.** When the run's geometry could not be measured, a run nobody chose an engine for takes the engine the declarations name for its flow (or the flow-only order). |
| ENG-9 | in force | **The user confirmed an engine the measured ranking did not put first** (for example, the ranking was not ready while the user was asked). The confirmed engine stands. This is a gap D1 closes: the proposal should always be the ranked one. |

## SW: whether a run moves to another engine after a failed attempt

Decided by `pipeline/engine_fallback.decide`. The run moves only on measured facts, never on a
review. The order the run moves in is ENG-5.

| ID | Status | Rule |
|---|---|---|
| SW-1 | in force | **Move on: the mesh came out broken** (checkMesh's fatal defects). The next engine in the ladder runs at once. |
| SW-2 | in force | **Move on: the engine could not build a mesh** (it crashed, stopped early or refused the input). |
| SW-3 | in force | **Move on: the same measured failure repeated** on this engine. |
| SW-4 | in force | **Move on: the shared attempts go to the untried engine** when a retry here would leave it no attempt of its own. |
| SW-5 | in force | **Stay: a measured check failed, and this engine's own levers are tried first**, because a retry here still leaves every untried engine an attempt. |
| SW-6 | in force | **Stay: a retry here fits** and still leaves every untried engine an attempt. |
| SW-7 | in force | **Stay: a review never moves the run.** The mesh passed every measured check. |
| SW-8 | in force | **Stay: the engine is not ours to change** (the user named it, or a dispute; see ENG-6). |
| SW-9 | in force | **Stay: another engine cannot change this failure** (the request, the approval or a region split), or the mesh is sound and only short of one of our own bars: its own resolution ladder answers it (LAD-cfd-1), never a switch. |
| SW-10 | in force | **Stay: no untried engine delivers the approved mesh** (same boundaries, units, cell kind and layers). |
| SW-11 | in force | **Stay: the untried engines would refuse** this many separate passages in one job. |
| SW-12 | in force | **Stay: no regular attempt is left.** |
| SW-13 | retired (D3) | **Stay: too little time left** for the next engine's run. Retired: no clock decides a switch any more (TIME-1). A next engine that runs past the run's guards is a guard trip (TIME-3). |
| SW-14 | in force | **Stay: the fallback ladder is switched off** by a setting. |
| SW-15 | in force | **No decision: the last attempt did not fail.** |
| SW-16 | in force | **Move on, to another kind of mesh: the system's own pick made no mesh, or a broken one** (a time-out, a crash, a stop before meshing, broken cells), and no untried engine delivers the same kind. The next engine in the ranking takes the run when the only differences are the mesh's file format and cell type: never fewer layers, a worse wall fit, a lost requirement or a setting. The user is told what changes, as it happens and beside the delivered mesh. Never for an engine the user named (ENG-6). |
| SW-17 | in force | **Move on: the mesh was built, a check refused it, and another pass on this engine could not change that** (LAD-cfd-8, `pipeline/engine_fallback.GATE_LEVERS`). The check is named in the record. An untried engine that delivers the same approved mesh takes the run; SW-2 stays for an engine that built nothing. |

## DEL: which valid mesh a run delivers

When a run built more than one valid mesh, `application/review_delivery.rank_key` ranks them by a
fixed order of measured facts. The first fact that separates the winner from the runner-up is the
rule. An invalid mesh is never delivered.

| ID | Status | Rule |
|---|---|---|
| DEL-0 | in force | **The only valid mesh** the run built is the one delivered. |
| DEL-1 | in force | **A mesh the review confirmed is the wrong problem ranks last** (a cited, inspected wrong-problem finding, not a concern). Shadow period only: once `VERDICT_BY_LIMITS` is on, a review ranks nothing and this position never separates two meshes. |
| DEL-2 | in force | **A mesh that passes every fixed quality limit beats one that does not.** |
| DEL-3 | in force | **Fewer failed quality checks wins.** |
| DEL-4 | in force | **Meeting more of the approved plan wins** (layers on the wall, wake refinement, stated sizes). |
| DEL-5 | in force | **Better worst cells win**, compared to the whole degree of non-orthogonality. |
| DEL-6 | in force | **On a measured tie, the mesh whose review passed wins.** Shadow period only: once `VERDICT_BY_LIMITS` is on, a review ranks nothing and a tie on everything measured goes to the earlier attempt (DEL-10). |
| DEL-7 | in force | **Lower worst non-orthogonality wins** (exact value). |
| DEL-8 | in force | **Lower worst skewness wins.** |
| DEL-9 | in force | **More wall covered by prism layers wins.** |
| DEL-10 | in force | **The earlier attempt wins** when everything measured is the same. |

## VER: pass, delivered with concerns, or fail

Decided by `contracts/decision_record.verdict` from measured numbers alone, read off the delivered
mesh by `engines/verdict_limits.py`. Every finished run's why record carries one `verdict` entry:
the outcome, the VER rule, and every row below with its measured number, its limit and its
source, so the verdict replays from the record. Nothing the AI reviewer wrote is an input.

**The AI reviewer only adds notes.** It still looks at the pictures. Its points are shown to the
customer under "Reviewer notes", each one labelled "Reviewer note". It cannot change a status,
start a rebuild, a bonus attempt or a retry, rank one mesh over another, or fail a job as the
wrong problem. A user's own dispute ("rebuild it") is the user's decision and still rebuilds.

**Shadow first.** The setting `VERDICT_BY_LIMITS` (off by default) switches the limits verdict on.
While it is off, the review-led verdict still decides, and the limits verdict is worked out on
every run beside it: one `verdict shadow:` log line (limits outcome, rule, review-led outcome,
whether they agree, the limits missed) and the `verdict` entry in the why record.

**On for dev.** The deploy target turns it on for shared dev and every personal environment
(`verdict_by_limits` in `.github/workflows/deploy.yml`, sent to the workers as template metadata,
so a fleet deploy applies it). Prod keeps the default until dev has run with it.

| ID | Status | Rule |
|---|---|---|
| VER-1 | in force | **Fail: no valid mesh.** The executor's gates refused the last attempt, or the mesh's own numbers fail one of the engine's gating rows (its `criteria.py` rows marked gating: checkMesh fatal defects, wall captured, ports captured, the quality floors, regions and interfaces). An invalid mesh is never delivered. Invalid is what checkMesh v2412 itself fails on validity, read the same way in every OpenFOAM engine (`engines/checkmesh_validity.py`): negative-volume cells, wrongly oriented faces, open cells, empty patches on a 3D mesh, zero-area faces, faces 90 degrees or more out of square (checkMesh's non-orthogonality errors), faces out of upper-triangular order, unused points, duplicates, points out of range and broken topology; skewness, aspect ratio, determinants and weights stay quality. Two zero-area faces and two faces at 118.7 degrees on a cfMesh manifold (board batch 3), five and five on a cfMesh cooling pipe (batch 2), had been read as no defect and delivered with concerns; the cfMesh rescue had even kept the manifold's broken mesh as its best. The resolution floor, the share of skewed faces and the one-job cell limit are not validity: on a sound mesh they are notes (LAD-cfd-3, LAD-cfd-4). |
| VER-2 | in force | **Delivered with concerns:** the mesh is valid but misses at least one production limit (table below). Each one is listed as measured vs limit. |
| VER-3 | in force | **Clean pass:** valid, and every production limit that applies is met (a limit whose number was not measured is listed as unmeasured and decides nothing). |
| VER-4 | in force | **Wrong problem, by measured checks only.** The run failed at a gate that measures one of the ways a mesh can be a different problem than the one confirmed (table below). The gate's own measured account is what the user reads. |
| VER-5 | in force | **A review never reruns or fails a run once the limits decide.** When a mesh passed every gate, its review ends the run whatever it said, and also when it did not conclude (the model was busy, down, or gave no answer). No review rerun, no rebuild, no failure: the measured limits decide. A crash after the review is rescued the same way, whatever the review said. A user's own dispute keeps its routing. |
| VER-6 | in force | **The recorded review verdict is the measured one once the limits decide.** A review that ran on a mesh every gate passed records PASS (job row and final result) when the measured limits deliver it, pass or pass with notes. The model's own call is kept beside its notes, labelled. Job fb44fed7 recorded the model's FAIL on a valid FEA mesh. |
| VER-7 | in force | **A reviewer point a measurement settles is not an open point.** When a review axis is about a property a measured row measures exactly (layer coverage, cell quality, regions, interfaces, passage resolution, FEA element validity and detail, the FEA face accounting), and that row was measured and met, the point is kept with the measurement that settles it, and is not shown as a note to act on. A point no measurement speaks to stays a note. |
| VER-8 | in force | **The mesh on disk is the case written last, never the one whose name sorts last** (`engines/surface_deliverable._patch_files`, read by the CAD check, the delivered surface and the port areas). Every snappy pass writes its boundary to VTK/<its case>_<time>/; a pass the size brake stopped leaves its own beside the delivered one, all at time 0. The boundary read is the newest case's (by when its files were written), at its latest time. RM3 on 470350f3: two stopped passes (far field only) sorted after the delivered case by name, and the CAD check read no body off a 6.05 M-cell production-grade mesh (RM5 before it: "100% of your CAD not reached"). |

### VER-2 production limits, per engine and purpose

| Limit | Engines | Applies to | Limit value | Source |
|---|---|---|---|---|
| Worst face non-orthogonality | snappy, cfMesh, multi-region | every flow | at most 70 degrees | checkMesh warns above 70 |
| Worst face non-orthogonality | VMTK | every flow | at most 70 degrees | VMTK's own quality record, measured as checkMesh measures it (`engines/vmtk/vmtk_runner.check_mesh`); the same bar as the other flow meshers |
| Worst face non-orthogonality | gmsh | external and internal flow (not FEA) | at most 85 degrees | gmsh's own gating bar, so a mesh past it never validates |
| Share of skewed faces | snappy, cfMesh | every flow | at most 0.05% | checkMesh's skewness bars as a share of all faces; a production limit on a sound mesh, never a validity bar (cfMesh often does not report it) |
| Wall covered by prism layers | snappy, cfMesh, multi-region, VMTK | when the approved plan builds layers | at least 80% | lab history: below it wall shear and y+ are unreliable on a material share of the wall |
| Layers built short of the layers asked | cfMesh | when the approved plan builds layers | none short | the layer census (layers in the meshDict vs the request) |
| Connected cell regions | snappy, cfMesh, gmsh, VMTK | every flow | at most 1 | checkMesh's region count: a second region is cut off from the flow |
| Cells across the narrowest passage | snappy, cfMesh, gmsh, VMTK | internal flow | at least the resolution floor (12) | the resolution floor's own reading; narrow side passages it set aside are listed here |
| Stated requirements met | every engine | every flow | no near-miss | the executor's measured requirement checks (`requirement_caveats`) |
| A believable size for what it is | every engine | every flow | no size concern | the unit-plausibility check on the delivered body |
| Follows the CAD it was built from | snappy, cfMesh, gmsh | external and internal flow | no measure missed | `engines/cad_fidelity.py`: the share of the mesh's wall more than one cell off the CAD (2%), the share of the CAD more than two local cells from the mesh (1%), the volume against the CAD's (3% internal, 5% an external body), each opening against its confirmed area (0.9 to 1.1); a measure that could not be read is unmeasured. A mesh past the rebuild bars is refused by the `cad_fidelity` gate (VER-4) |
| The engine's own declared advisory lists | snap-grid | every flow | empty | `engines/snapgrid/criteria.py` (thin layers short, resolution short) |
| Worst scaled Jacobian, over the whole curved element | every FEA adapter (gmsh today) | a mesh built from an FEA plan | at least 0.2 for straight (4-node) tetrahedra; at least 0.01 for curved (10-node) ones | Cubit/Verdict's acceptable range for straight tetrahedra. A curved element's figure reads its curving as well as its shape, and none of the version-1 solvers checks it (they check validity), so a curved mesh is noted only under 0.01 (Areen, 22 Oct) |
| Worst Jacobian ratio across an element's nodes | every FEA adapter | a mesh built from an FEA plan | at most 30 | Ansys MAPDL's corner-node warning |
| Worst aspect ratio (1 is a perfect element) | every FEA adapter | a mesh built from an FEA plan | at most 20 | Ansys MAPDL's aspect-ratio warning |
| Angles between the faces of an element | every FEA adapter | a mesh built from an FEA plan | between 5 and 170 degrees | Hexera's internal gate (design section 9) |
| Mesh zones short of the FEA plan's rules | every FEA adapter | a mesh built from an FEA plan | none | `engines/fea_checks.py`: elements per quarter-turn and through the wall at each hot spot |

The FEA rows are the strictest limit among the version-1 solvers (Abaqus/CalculiX, Nastran, Ansys;
`engines/fea_quality.LIMITS`, read by `engines/verdict_limits.fea_limits`), measured on the solver's
own element (`engines/fea_quality.py`). For an FEA mesh, VER-1 also refuses any inverted element
(a Jacobian not above zero anywhere in the curved element) and any degenerate one: a VALID MESH is the only thing that fails an FEA run (Areen, 21 Oct). The rows above, the quality note floor (SICN 0.1 for straight elements, 0.01 for curved ones) and the elements through each wall are notes on the delivery, never a failure.

The table is `engines/verdict_limits.PRODUCTION_LIMITS`. A limit names engines and flows, never a
file, a part or a model. Changing a number here means changing the table, this book and the
version in the same PR.

### VER-4 measured checks

| Way the mesh is the wrong problem | Measured by | Today |
|---|---|---|
| The wrong side of the body was meshed | `port_areas`, `region_contract` | gates |
| Part of the confirmed geometry is missing | `file_fidelity`, `cad_fidelity` | gate (snap-grid; snappy, cfMesh and gmsh flow meshes: over 8% of the CAD more than two local cells from the mesh, or the volume over 25% off) |
| The wrong scale | the believable-size row of VER-2 | a concern, not a failure |
| The flow setup contradicts what was confirmed | `domain_extent`, `port_areas` | gates |
| A boundary contradicts what was confirmed | `patch_contract`, `boundary_types`, `port_areas` | gates |

The table is `contracts/decision_record.WRONG_PROBLEM_CHECKS`.

## TIME: planned work decides, the clock only guards

A run must come out the same on a quiet machine and on a busy one. So **planned work** decides
what a run does: cells, iterations, triangles, samples, ladder steps and attempts. These are the
same on every machine. A clock is kept only as a **guard**, so a hung step cannot hold a machine
forever. The numbers live in `contracts/work_limits.py`. Every guard's planned work and size goes
into the run's why record as a `work_limit` entry, and every trip as a `guard` entry. Both replay
from their recorded inputs.

| ID | Status | Rule |
|---|---|---|
| TIME-1 | in force | **Planned work decides, never the clock.** A step runs its planned work to the end. Whether a step or a ladder rung runs, how coarse a pass is, which engine runs next and what the verdict is never depend on how long anything took. |
| TIME-2 | in force | **Each guard is 3 times the planned time.** Planned time is the planned work divided by the step's slow rate (the 10th percentile the lab measured: snappy 1,500, cfMesh 1,200, VMTK 4,000 cells a second). A guard is never shorter than the step's fixed cap before D3, so nothing that finished before is cut now. It is never longer than the ceiling the job around it allows. An engine with no lab rate keeps its old cap. A run watched for progress (RUN-5: snappy, cfMesh, VMTK, multi-region snappy, gmsh, snap-grid) has its machine's wall as its guard, and inside it is stopped only when it makes no progress for the stall window; that stop is a guard trip too. |
| TIME-3 | in force | **A guard that trips is an infrastructure failure.** The attempt ends and nothing on disk is judged. The same attempt is run again once, unchanged - except a trip that says the step would do the same work again (TIME-13). A second trip ends the run as "ran out of time". A trip never picks a lever, skips a step, makes a pass coarser, picks or switches an engine, or changes a verdict. The exceptions are TIME-8 (a trip once the attempt already holds a valid mesh keeps that mesh) and TIME-14 (a trip inside one passage's rescue keeps that passage as built). |
| TIME-4 | in force | **A wait that feeds a decision waits for the answer.** This covers the measured engine order, the intake's recommendation and the geometry check's naming. Their guards are long (15, 5 and 9 minutes). A trip counts as that step failing, the same path as any error in it. It is never a different answer chosen because time ran out. |
| TIME-5 | in force | **The job's own clocks are guards only.** These are the builder's 3,600 s per attempt and 9,000 s in total, the pipeline's 21,600 s, the reviewer's 1,800 s and the Cloud Run task's 4 hours. A trip ends the attempt or the run as ours ("ran out of time"). The builder's and the pipeline's trips are recorded as guard trips; the reviewer's ends the review as one that did not conclude (our failure, never a verdict). (The snappy planner's 1,800 s setting is read by nothing.) |
| TIME-6 | in force | **The CAD repair steps still decide by the clock: inspection (25 s) and repair (120 s).** If inspection runs out, the repair status is "inconclusive". If repair runs out, the original file is meshed. These steps belong to the repair work (#201). They are recorded as `time_limited` with source `guard-clock`, and they are left for that work to bound by face count. |
| TIME-7 | in force | **A repair step on a finished mesh is planned work too.** The cfMesh rescue's optimiser (`improveMeshQuality`) runs a number of loops planned from the mesh's cells: 40 million cell-loops in all, never more than 20 loops and never fewer than 10 (cfMesh's own default). So a 2 M cell mesh gets 20 loops and a 4 M cell mesh 10; the rescue asked 50 before, whatever the mesh. On 8 dev-side meshes (29 Oct), 6 untangled in 2 or 3 loops (50-140 s), and on the 2 tangled ones the bad faces stalled at 3-19 from loop 2-5 while each loop cost more (1.4 M cells: 498 s for 20 loops, 1,263 s for 29). It also stops itself, read from its own count, when it is not untangling: at its 3rd untangling loop its bad faces are still at least a tenth of its 1st loop's, and at least 1,000 (on every dev-side mesh it untangled, loop 3 was under 3% of loop 1; the benchmark's microfluidics spiral read 52,518, 35,250, 52,544, at 6 minutes a loop). What it left is not kept, and the rescue goes on with the best mesh measured so far. Its guard is 3 times that work at its slow rate (5,000 cell-loops a second: a loop's cost follows the tangled region); the protective re-mesh is guarded like a cfMesh run of the same cells; neither guard is ever past what is left of the run's. Before (full benchmark, 29 Oct), the optimiser ran its 50 loops whatever the mesh, under the run's 4-hour guard: on tangled 2.5-4 M cell meshes it ran 2.5 to 3.7 hours and tripped, and 4 files main delivered came back as "ran out of time". The numbers were set on dev-side files only. |
| TIME-8 | in force | **A trip never throws a valid mesh away.** When a guard trips after the attempt already holds a valid mesh, that mesh is kept, with a note, and the attempt goes on to its checks as usual. It is never replayed or ended as "ran out of time". Valid means measured with no fatal defect: in the cfMesh rescue, the mesh as built or a better candidate measured before the step that tripped; in snappy, an earlier pass's sound mesh kept aside; for the passage flow reading and the passage measure, the mesh they read (which is checked without the reading, as before the reading existed). That reading is never taken beside a mesh with a fatal defect, which fails its gate whatever the flow does. With nothing valid in hand, TIME-3 holds. The trip is still recorded (rule TIME-8, with what was kept), so the run's record shows the guard fired. |
| TIME-9 | in force | **The staged VMTK wall's triangles follow its area, never the CAD's tessellation** (`engines/vmtk/rims._halve_long_edges`). The wall is cut so no edge is longer than its bound by halving edges round after round, which keeps each triangle's shape. A needle - two edges past the bound, the third within it, and thin (longest edge squared over twice its area above 20) - is taken out of the halving the round it appears: its two long edges get exactly the points the halving puts on them (2^k equal pieces, shared with whatever is on the other side, so the wall stays conforming and every rim keeps its points), and the two chains are zipped from the apex into a ladder, each quad cut along its shorter diagonal. A needle of 2^k pieces a side is 2^(k+1) - 1 triangles; halved, it was 3^k. Why: OCP tessellates a long straight bore as slivers the whole length. abc 00168427 (a 4 m pipe, 56 mm bore) came as 284 triangles and left the halving as 2,868,474 at an 11.2 mm bound (an 11 mm wall needs about 14,000), short edges down to microns; the radius field took 712 of the 868 s of staging on the laptop, 99 minutes on the board, and with 00160152 and 00184527 the run met the 250-minute wall with no mesh. Laddered: 159,908 (vmtk's own remesh makes about 100,000 of it at its target edge). |
| TIME-10 | in force | **VMTK's staging is planned work, and a wall that cannot fit the run moves it on** (`engines/vmtk/staging_work.py`, `rims.TooManyTriangles`). Each triangle the staging hands VMTK costs it, at its slow rate, 6.5 ms of surface work - the radius field the staging reads on it and vmtk's own remesh and centerlines, which run on the staged wall before any cell is filled (board, 22 Nov: 2.3 ms a triangle on abc 00046345, 1.8 on 00178394, 6.4 on the stabilizing rod). The staging and that work get one hour of a run (a quarter of the 4-hour mesh job, so the next engine has the rest to deliver), so the staged wall is at most 553,846 triangles. The edge bound counts what each round will make before it makes it and stops at that count; the bounded wall is priced before the radius field reads it. Past it, the staging stops before the work starts, as the staging's own refusal (deterministic, before meshing), in plain words ("VMTK would have to prepare at least N wall triangles from the M of your surface, about H hours of work, past the 1 hour a run gives it..."), and the run moves on to the next engine at once (NOT_BUILT, SW). The planned work is recorded with every staging (`vmtk_staging.json` `staging_work`). Why: abc 00168427, 00160152, 00184527 and 00046344 staged 3.0-3.6 M triangles, spent 81 to 134 minutes staging, and met the 250-minute wall with no mesh; 00088953 spent 100 minutes staging 574,866. |
| TIME-11 | in force | **The cfMesh rescue runs its cheaper lever first and never optimises a mesh the best so far already beats** (`engines/cfmesh/rescue.remesh_first`, `RESCUE_ORDER_RULE`). The order is decided from planned work at the slow rates, never the clock: the protective re-mesh is one cfMesh run of the cells, the optimiser its planned loops over them, so the re-mesh runs first, and a re-mesh that comes out off the edge is kept with no optimiser run at all. The optimiser then takes the candidates still near the edge, best first, and skips one the best so far beats (recorded as `skipped`, rule TIME-11). abc 99768 (c2e8_p30a): the optimiser ran 2,729 s into its guard on a re-mesh of 171 degrees with negative volumes, beside an optimised mesh of 87 degrees with no fatal defect; the rescue took 4,574 s. INS-30 holds: every candidate still keeps every opening the mesh as built held. |
| TIME-12 | in force | **cartesianMesh is stopped when its untangling is not converging, read from its own counts** (`engines/cfmesh/native.untangle_not_converging`, `UntangleWatch`, `UNTANGLE_RULE`). cfMesh untangles in passes of at most 50 iterations and prints its bad faces at each. Once two passes of the run have ended with bad faces left, a pass still at 1,000 bad faces or more that, at the geometric rate of its last 10 iterations, would need more iterations than it has left is stopped; the builder records ENGINE_CRASHED with untangle_not_converging and the run moves to the next engine, as VMTK's layers do. Never the clock: the same log stops at the same iteration on any machine. static_mixer_004 (c2_res5t): 4,531 s of 5,514 s in 108 passes, the last rising to 64,438 bad faces and ending at 2,107; the mesh was refused anyway. |
| TIME-13 | in force | **A step its own guard stopped is not run again on the same plan** (rulebook 84; `engines/cfmesh/rescue._trip` `same_on_replay`, `contracts/work_limits.after_trip`, `TIME_SAME_ON_REPLAY`, `pipeline/graph._after_guard_trip`). A cfMesh rescue step stopped by its own guard (3 times its planned work, not cut short by what was left of the run's guard) works on the same mesh with the same planned work when the attempt is replayed, so its trip says `same_on_replay` and the run ends at once as ran out of time (TIME-3's one replay is not spent; an earlier sound mesh is still delivered, LAD-cfd-3). abc 99768 (c2e11_p33a): passage 1's optimiser on 26,407 cells (6,347 faces pointing the wrong way) was planned 105.6 s, guarded 316 s, tripped, was run again unchanged and tripped again - about 12 minutes spent on a replay that could not end otherwise. | TIME-14 | in force | **A guard trip inside one passage's rescue belongs to that step, not the attempt** (rulebook 85; `engines/cfmesh/rescue.rescue` `step_only`, `engines/cfmesh/native.rescue_passage`, `_note_passage_trip`, `passage_trip_words`, `contracts/work_limits.TIME_PASSAGE_STEP`, `NOT_ATTEMPT_ENDING`). A trip of the whole mesh's own rescue still ends the attempt (TIME-3 / TIME-13). abc 99768 (c2e13_p34d): passage 1's optimiser tripped at 21:20; the attempt went on, its whole-mesh rescue finished a mesh in 2,115 s (worst cell 85.4 degrees), and the executor threw it away for the earlier passage trip ("an infrastructure stop, nothing judged"); the wrap fallback then left an incomplete polyMesh at 53.3 min. |

## PLAN-cfd: the flow mesh's sizing, on every flow engine

The sizing rules every flow engine (snappyHexMesh, cfMesh, VMTK, gmsh) follows for a CFD mesh,
from the part's own measured passages - never from a file or a part name
(`engines/resolution_policy.py`, `engines/gap_sizing.py`).

| ID | Status | Rule |
|---|---|---|
| PLAN-cfd-1 | in force | **Cells from the measured narrowest gap, locally.** Every passage the flow goes through gets at least 13 cells across its own width, refined only where it is narrow: snappyHexMesh and cfMesh refine boxes and distance bands round the narrow spots of the staged wall (`engines/gap_sizing`, the cost checked against the cell limit before meshing); VMTK sizes every edge from the local radius (2 / `edge_length_factor` across); gmsh sizes from the local radius field. The plan is written beside the case (`gap_sizing.json`) and cited in the why record. |
| PLAN-cfd-2 | in force | **Every opening, at least 8 cells across its own width.** A port narrower than 8 wall cells gets its own finer cells at the port only (snappyHexMesh: the port's refinement level; cfMesh: a local refinement on the port's surface). Under about 4 the octree seals a port over and it comes back with no faces. |
| PLAN-cfd-3 | in force | **The big-machine hook.** When the cells the sizing rule needs are over the run's cell limit (the standard machine's, or the user's own count), the plan records `route_big` (and the why record cites it), the run is meshed as the limit holds, and the delivered note says so in plain numbers. NOTHING IS ASKED (Areen, 14 Nov: "the person is specifying how many cells they want - why does the system ask 8 M or 21 M?"): the "Keep 8.0 M, or try full detail?" question and its buttons are gone. The bigger machine is the user's to ask for, by a count in their words (RUN-9); the note says how many cells to ask for. |
| PLAN-cfd-4 | in force | **A size the user asks for on a part becomes that part's own level (snappyHexMesh)** (`engines/snappy/part_levels.py`). On a surface of several named parts, the notes are tied to the parts by NOTE-4 (the reading the user checked before approval first, NOTE-5). A size becomes a level against the background cell the dict really uses: the coarsest level whose cell (base / 2^level) lies inside the user's range, else round(log2(base / size)) at the range's middle; "finer" is one level over the surface's own, "coarser" one under. A part that is its own region in the staged surface gets its level there (finer or coarser). A part merged into one wall with others is refined near its own surface (a distance region on its own file, 3 cells deep) and cannot be made coarser: that is said, not applied. What the notes asked and what each part got is said once per run (in cell sizes, not levels) and kept in the why record. Unclear words, one part, or no answer: nothing applied - never a failed run. |
| PLAN-cfd-6 | in force | **The far field is wide enough for the body: at most 3% blockage** (`engines/far_field.grow_for_blockage`, `projected_areas`, `blockage_words`; `engines/snappy/snappy_runner.domain_from_strategy`, `engines/snappy/drivers._say_blockage`, `engines/cfmesh/cfmesh_runner._configure_external_3d`). The margins asked or proposed (5 / 10 / 5 body lengths up, down, to the side) are the minimum. The body's frontal area along the flow (half the summed absolute projection of its staged wall, the measure the CFD board uses) must be at most BLOCKAGE_MAX (3%) of the box's section across the flow (COST Action 732, Franke et al. 2007; the usual wind-tunnel correction limit): when it is not, every open cross-flow face moves out by the same distance until it is (aimed at 95% of the limit). A floor under a grounded body and a symmetry plane never move; the streamwise margins are untouched. Wide, flat and rotating bodies thus get their box from their frontal size, not only their length (the board's external sweep, 22 Nov: 13 of 120 at 3.05-12.6% with the box always exactly 5 / 10 / 5: 5 propellers or rotors, a wind turbine, 4 road vehicles, a rocket, a bridge, a bluff body). Said in the run log ("the far field was widened by 3.4 body lengths on each open side so the body blocks 2.9% of its cross-section (it was 9.8%; at most 3%)") and kept beside the case (`far_field_blockage.json`). The extent gate reads more room to the side than asked as no defect (the typed path already did; the prose path's lateral check is one-sided). cfMesh widens a free body's box the same way (a box with a floor or a symmetry plane is left as planned there). |
| PLAN-cfd-7 | in force | **The near wake and the flow beside the body are resolved for every body** (`engines/wake_region.plan_wake`, `level_for_cells`, `plan_near_body`; `engines/snappy/snappy_runner.render_snappy_case`). On the wake length (the reference length, the length along the flow, or a disc's smaller cross size, whichever is largest): the finest wake box keeps at least NEAR_WAKE_CELLS (25) cells per wake length - finer than one level under the wall where the wall's own cells are coarse for the body, never finer than the wall - and reaches NEAR_WAKE_REACH (1.5) wake lengths behind the body. A budget cut takes the far wake first (shorter down to that reach, then the outer boxes, then the near wake one level coarser down to its floor) and never past the floor; what the protected near wake costs over the wake's share is added to the budget, within one job's cell limit. Before, the cuts halved every box's reach first, so the near wake ended short of one body length (the board's external sweep: 29 of 120 under 25 cells per body length 1 L behind, 4.8-24). A box round the body's own box, NEAR_BODY_PAD (0.1) wake lengths past it, holds NEAR_BODY_CELLS (50) cells per wake length beside the body (never finer than the wall; the board: 29 of 120 under 50 there), its cells added to the budget the same way. A wake level the plan or the user asked coarser keeps the old cuts; a cell count of the user's is never raised. Recorded in the wake record (`near_wake`, `raised_cells`, `near_body`). |
| PLAN-cfd-8 | in force | **A cfMesh internal plan over its budget is made coarser only where that buys cells, its narrow-gap boxes are held as they are priced, and a plan still over runs where it fits** (`engines/cfmesh/cfmesh_runner.coarser_wall`, `machine_for_plan`; `engines/passage.narrow_passage_regions(whole_box=)`). A level coarser at the wall is taken only when it cuts the estimate by a quarter or more (`MIN_LEVEL_CUT`) and leaves at least two cells across the typical passage (`USABLE_WALL_CELLS_ACROSS`); a plan line never says "about 0 cells". When the gap plan cannot fit even its fewest cells across, the fallback boxes are held to half the job's cells (the run's budget, or the standard limit when none is set) and costed at their whole volume, as cfMesh refines a box and as the plan prices it. An internal plan still over the standard machine once nothing more can be made coarser says what it comes to and what carries it, and runs on the VM whose memory holds it (RUN-9's route). Why: abc 00063401 priced 210 M cells, 209.3 M of them in 114 narrow-gap boxes about 250 times their fluid, held by no budget (none was set) and costed at their fluid; eight wall levels (0.85 mm to 218 mm) cut it to 209 M, left 0.06 cells across the typical passage, and the run was sent to a 64 GiB VM for files alone. Tests: tests/unit/engines/test_cfmesh_plan_coarsening.py. |

## LAD-cfd: the resolution ladder, and what a sound mesh becomes

A mesh is SOUND when every blocking gate passed and the trial solve converged: no fatal checkMesh
defect, no negative volume, every port with faces, the right region, the domain asked for. The
resolution floor (12 cells across the narrowest 5% of the wall), the share of skewed faces and the
one-job cell limit are our own bars, not validity: on a sound mesh they are notes, declared as
non-blocking gates (`GateSpec.blocking=False`). `engines/resolution_policy.py` holds the rules.

| ID | Status | Rule |
|---|---|---|
| LAD-cfd-1 | in force | **The ladder's next rung, never an identical re-run.** A sound mesh short of the resolution floor sends the next attempt up one rung on the same engine: the cells-across target at the narrow spots is multiplied by 1.5 (rung 1), then 2 (rung 2), or by what the measured shortfall needs ((floor + 1) / measured) when that is more, never past 3. snappyHexMesh also refines where the mesh measured short (its narrow retry); cfMesh detects and sizes its narrow-spot boxes that much finer; VMTK divides its edge factor by it, and its budget fit may coarsen the edge back only to the rung's own cells across (a rung that cannot fit one job is not started, and the sound mesh stands); gmsh sizes its passage field by it. The rung is written into the attempt's workspace (`resolution_ladder.json`), so the case the mesher gets is never the one it already ran (the rerun guard hashes it). No rung when there is no room left to refine: the mesh already has 90% of the cell limit, or the attempt's gap plan was already held by the limit (`limited`, `over_limit`, `accepted_fewer`) with its budget the whole one-job limit - the next plan has the same cells to share and shares them the same way (lab: 7 of 7 such rungs rebuilt the same mesh). A held plan under a smaller budget keeps its rung: the next plan may raise the budget. |
| LAD-cfd-2 | in force | **A switch does not spend the ladder.** When the run moved to another engine and that engine's first mesh is sound but short of the floor, it still gets one rung - inside the run's ceiling of 3 attempts. The time left never decides it (TIME-1, since D3): the run's deadlines are guards only (TIME-5), and a rung that runs past them is a guard trip (TIME-3); the earlier sound mesh is still delivered (LAD-cfd-3). |
| LAD-cfd-3 | in force | **Ladder spent, mesh sound: delivered with a note.** The note names the narrowest gap, where it is, its cells across and the floor ("the gap at (x, y, z) has 8 cells across; 12 is our floor"). The share of skewed faces is a production limit (VER-2), not a failure. And a later attempt that comes out broken never throws an earlier sound mesh away: the run delivers its best sound mesh instead of the failure (`node_deliver_sound`). The best is the one with the most cells across its narrowest gap (one that meets the floor beats any that does not), the newest on a tie; and when the last attempt is sound but a rung left it coarser than an earlier sound mesh, the earlier one is delivered too. The same holds between snappyHexMesh's own passes: a sound pass is kept aside while the next pass tries for a cleaner one, and put back if that pass comes out broken. |
| LAD-cfd-5 | in force | **The last rung: a wrapped surface, only when every rung before it failed** (`pipeline/cfd_wrap.py`, `cad/surface_wrap.py`; STAR-CCM+'s surface wrapper, Fluent Meshing's wrap). When a flow run (external or internal) is about to end with NO MESH - every regular attempt and every switch of the fallback ladder spent, a failure no retry of these engines changes, or the run's time spent - and no earlier attempt is sound (LAD-cfd-3 comes first), the surface the engines staged is wrapped into a clean skin and meshed again, as any attempt is: same boundaries, same plan rules, layers where they hold, the same gates. **The rung has its own engines, in order**: the engine the user named when it is snappyHexMesh or cfMesh, then those two in the run's ranked order (ENG-5), then gmsh's tetrahedra filled against the skin's own triangles with no remesh and no layers - each only when it admits the approved request. A step that fails on the wrapped surface hands the same skin to the next engine (a user-named engine too: the skin is clean, so the engine is all that is left to change), and the delivery says which engine failed and which took over; a mesh from gmsh's step is labelled DEGRADED (tetrahedra, no wall layers). **The rung has its own time**: each step starts with at least `CFD_WRAP_TIME_S` (2 hours) ahead of it, whatever the earlier attempts spent, so a run that timed out still reaches it. Never for a failure that is not the geometry's (our service, the domain asked for, a boundary type or name, a region split, the review), a file the engines refuse by design, or a dispute rebuild; a failure of ours ends the rung. The wrap is for the mesh only: the customer's file is never changed, and INS-7's stop at the stage stands. A run that delivers a mesh today never reaches this rung. |
| LAD-cfd-6 | in force | **The wrap follows the CAD to within its distance, and closes no real passage.** The staged surface (flow round a body: the body; flow through a part: the staged fluid boundary, lids and INS-8 covers included, so a leak the user closed stays closed) is drawn on a grid of at most 32,000,000 cubes, each cube a 2.5th of the wrap distance r. The flow's side is every point farther than r from the surface that the flow reaches - from the grid's border round a body; through a part, from the point inside the flow, and when that does not reach every opening, every pocket of free space the staged boundary encloses (its generalised winding number at the pocket's deepest point at least one half), so shells drawn through each other merge and the staged boundary's own topology never decides - and the wrapped fluid is that space grown back by r: gaps narrower than 2r are closed, and faces that cross, doubled faces and the inside of overlapping shells, which the flow never reaches, are left out. r is the surface's diagonal over 500 (about half a standard wall cell); through a part it is never more than 0.15 of the narrowest way's half-width from the point inside the flow to every opening (measured on the grid), so a real passage keeps at least 70% of its width, and the flow must reach every opening in ONE connected fluid, else r is cut to 0.6 of itself, down to half a grid cube; still not, the whole is drawn once more on a GRADED grid of up to 128,000,000 cubes, so holes and vessels the openings need are resolved. A staged boundary left open (the flood gets out to the open air) is wrapped again at two, four and eight times the distance, never past the diagonal over 60. The fluid may be several separate passages (cfMesh meshes them side by side), each holding two openings at least. Holes finer than the graded grid are below any mesh's resolution and are closed by definition: they are listed with their size as bridged spots. When no try keeps every opening, the try that lost the fewest openings (then the least opening area) is delivered with a concern, never refused: only the passages still holding an opening are kept, and each stranded opening (cut off, or alone in a dead end) is placed on the wrap's wall nearest where it is drawn, with its drawn area, the delivery saying how far it moved. The rung stops only when the wrap finds no fluid at all. A grid the cap holds coarser raises r with it, to 2.5 cubes - or, where a passage asks for less (the narrowest way, or a flood that no longer reaches an opening), to one cube, so small vessels stay open on a coarse grid. Round a body the flow must stay outside it: when the space a wrap four times as wide (never past the diagonal over 60) seals off from the open air, and the flow at r still reaches, is more than a quarter of the body at that wider wrap, the flow went inside through a gap, and r doubles (at most three times); still inside, the rung stops rather than mesh the body hollow. A sheet the flow wets on both sides seals nothing off, so it is never taken for a hollow body: it is kept as a slab about 1.5 cubes thick. The skin is the zero level of the distance to the wrapped fluid's edge, which equals minus the exact distance to the surface wherever the surface was sound, so it lies on the CAD to well under a cube there. It is closed and manifold (every edge on two faces, run opposite ways), its pieces enclosing fewer than 8 cubes dropped, every face turned out of the fluid (out of the body, round one), and coarsened (topology-preserving decimation) to about the triangles of edge 0.7 r its area holds, 20,000 to 600,000, only when the coarsened skin is still closed. Each face is named after the nearest face of the original, so every boundary keeps its name; a wrap that loses an opening stops the rung. |
| LAD-cfd-7 | in force | **The delivery says how far the wrap lies from the CAD.** Measured at every corner of the wrap against the original's exact surface: the largest and the 95th-percentile distance where the wrap lies on the CAD (within 1.5 cubes), and over all of it; every BRIDGED spot (a connected stretch farther than 1.5 cubes: a gap it closed, a sharp re-entrant corner it rounded) with its place, area, widest distance and the patch it was named after, the widest first (20 listed, the rest counted); the wetted CAD's distance from the wrap and the CAD faces the flow cannot reach. The run's outcome says it in one sentence ("meshed on a wrapped surface: within 0.4 mm of your CAD everywhere except 3 bridged spots"), the three widest spots by place, why the engines could not mesh the surface as drawn, and that the file was not changed; the mesh report lists every figure and spot (`cfd_wrap_report.json` beside the mesh). |
| LAD-cfd-4 | in force | **Over one job's cell limit is a note, never a retry.** A sound mesh bigger than one standard job is delivered at the size its sizing rules asked for, with the note; a retry could only shrink it. The worker's trial solve is not run on it (its matrix outgrows the worker); checkMesh's fatal topology and a lean count of the mesh's connected regions (from its cell graph; one per passage meshed) stand in, and a disconnected pocket still blocks. |
| LAD-cfd-8 | in force | **A retry changes what was refused, or it does not run** (rulebook 75, `pipeline/engine_fallback.GATE_LEVERS`, `engines/gate_facts.py`). One table says, for each blocking gate, what the next attempt on each rules-planned engine (snappyHexMesh's driver, the cfMesh writer) changes for it: broken or badly shaped cells - the folds repaired where they were found, a stricter plan, cfMesh's own rescue; an opening built at the wrong size - that opening refined one level finer (snappyHexMesh) or given half its cell (cfMesh), read from the refused gate's facts the attempt leaves beside it (`gate_facts.json`, carried to the next attempt with the ports castellation sealed, `.sealed_ports.json`); a mesh that does not follow the CAD, a short trial solve that did not converge and a boundary type - nothing. A refusal nothing bears on is never rebuilt on the same engine: the run moves at once to an untried engine that delivers the approved mesh; with none, the run's best sound mesh is delivered with the refusal said. Before, the RM3 wave absorber's production-grade 6.7 M-cell mesh, refused for how closely it followed its CAD, was rebuilt for 87 minutes with only its cell budget moved and refused again. **A refused mesh may be delivered only on these refusals, and only when it is valid**: how closely it follows the CAD (never when more than half of the wetted CAD is missed, the wall lies off the CAD on more than half, or the volume is off by more than half - that is not the part, refused as before); an opening's built area (the opening named, its built area against the confirmed one); plain cell shape, the share of skewed faces or the worst non-orthogonality, inside the solver's hard limit (85 degrees; a missing wall, a crashed or timed-out build, missing layers or an unmeasured bar are refused as before); the short trial solve, only on a mesh every gate passed (a disconnected pocket still blocks). Every later gate must pass it too. It is delivered as concerns, never as a pass - the finding first, in plain words with its number, then the way on ("ask for finer cells at the walls in your notes (a size in mm)"; "check the opening on the geometry stage"; "run the solver with non-orthogonal correctors"). ## INS: the fluid's inside (where the fluid is, how it gets in and out)

One map per part drives every step below, so the steps cannot disagree (`cad/inside_space.py`).
The stage's openings, the stage's question, the staging's seals and seed, and the checks before
meshing all read it. Nothing here reads a file name, and no model decides any of it.

| ID | Status | Rule |
|---|---|---|
| INS-1 | in force | **The inside-space map.** The part's surface is drawn on a grid of at most 6,000,000 cubes (400 a triangle, never fewer than 1,500,000; a cube never finer than 1/5,000 of the part's diagonal). Every loop of the surface that could edge an opening - an open rim, or the outline of a smooth patch no face lies across - gets a cap, and the free cubes are flooded from the grid's border. A **pocket** is space the open air reached with no cap but reaches now only through caps; space no flood reaches even without caps is a closed shell's inside (the metal, or a body that is the fluid). A cap with open air on one side and a pocket on the other is a **mouth**. A cap with a pocket on both sides (a step in a bore, a barb's ridge) is taken away and the space flooded again, until none is left. A cap whose pocket runs less than 1/10 of the cap's width behind it (under 9 in 10 of its points) closes a dent in the outside and is taken away too. Of two mouth caps of one pocket that share most cubes, the tighter loop is the mouth; of two facing one way on one axis, one just behind the other (within its width, at about its size, or within two cubes at any size), the one in front is. Pockets lined on the same side by one piece of the surface cut along the mouths (at least 1/4 of each one's lining) are one pocket. A pocket holding at least 5% of the largest one's space is a **passage**; a smaller one is a side pocket. Surfaces of more than 2,000,000 triangles are not mapped (the shape rules stand). |
| INS-2 | in force | **Openings are the mouths.** Every mouth of a passage is an opening, of any shape or size; a mouth of a side pocket (a bolt hole, a blind dimple) is shown as not an opening, for the user to click. A loop too small for the grid (under 4 cubes across) is read by the hole finder's shape rules (`cad/open_ends`), so no small opening is dropped - unless the map reads the space ahead of it as the part's own inside (a port from a tube into the chamber round it). The STL upload, the stage's click and the staging read this one definition (`open_ends.find_holes`). A CAD part's face-read openings whose outside is the part's own inside (a step in the bore) are proposed as not openings, and a CAD part whose faces give fewer than two gets the map's mouths. When the map's openings differ from the shape rules' and only the shape rules' close the fluid in, the shape rules' are proposed, with a note. |
| INS-3 | in force | **The flow kind by rule.** The user says the fluid flows through the part: when the map finds a passage with two mouths or more, or two openings are confirmed (a body that is the fluid, with its lids), it is internal flow. When it finds neither, the stage asks one plain question - "This part has no openings or inside for fluid. Did you mean flow around it?" (or, for an inside with one mouth, that the fluid has no way through it) - with flowing around it the one-click way out. Never a job that can only fail. A part the map could not read is never asked (the intake asks). |
| INS-4 | in force | **The point inside the flow is the deepest point of the passage**: the cube farthest from every wall and cap (the first in grid order on a tie) of the passage most confirmed openings open, taken when the closed boundary's winding number there is one, at least 4 of 6 rays cross it an odd number of times, and it stands at least 2% of the smallest opening's radius from every face. For a body that is the fluid, the deepest point inside it. Otherwise the point is stepped in from an opening, as before. Never a model's guess, never a point in a wall. |
| INS-5 | in force | **Caps fit each mouth's own loop; nothing leaks.** Every mouth no confirmed opening claims is sealed into the wall before the fluid's side is read (a mouth just behind a confirmed opening, inside its footprint and no wider, is that opening's own throat and stays open). When the loop-by-loop vote cannot settle which side is the fluid's, the pieces that line the passage are the fluid's. When the map's own seals leave the boundary unclosable, the same openings are staged once more as the shape rules alone read the surface, kept only if that closes, and recorded. A cap is the lid of the loop's own points (flat, or pulled toward the smallest area when the loop is not flat); a ring-shaped mouth (a centre body in it) is stitched round its centre, or, when a loop does not turn once round the centre, joined to the outer loop by one bridge and clipped whole. Then the sealed check: every edge of the fluid boundary on exactly two faces, and a flood of the boundary from the point inside the flow stays inside it. A leak is located and named. A wide one - no thickening of the wall by up to four cubes closes it, so any mesher would fill the outside too - on a boundary that is open or crossed by its own lids stops the staging before meshing; a narrower gap (a mesher's own cells close it), or any leak of a closed, uncrossed boundary (a grid artefact at a gap finer than its cubes), is recorded only. The file is never patched: a gap that is not an opening, and that the user did not ask to close for the mesh (INS-8), is named as a CAD defect ("this needs CAD repair") for the CAD repair stage. A passage the confirmed openings do not close is refused with the place of the opening left open. |
| INS-6 | in force | **Every confirmed opening is its own patch.** Each one comes out of the staging as a patch with faces on the closed fluid boundary, or the staging stops before meshing and names it. |
| INS-7 | in force | **A broken surface is said, never healed.** The check counts the drawn surface's open edges that edge no opening (an open pipe end is an opening; a tear is not) and its loose pieces (each holding at least 1/200 of the skin); a CAD solid's B-rep is closed, so its skin's unwelded seams are not counted. ## FLOW: through the inside or around the outside

One authority decides whether a flow part is internal (the fluid flows through its inside) or external
(around its outside): `application/flow_kind.decide`. The check stores its verdict on the facts as
`flow_kind` - `kind` (internal, external or undecided), `flow` (the kind, or the best guess the stage
draws while undecided), `best_guess`, `confidence`, `by` (file, words, geometry, pictures or guess),
`rule`, `reasons` (plain words), `question` and the `input_kind` that goes with it - and the proposal,
the stage and the intake read that one value. The measuring step's own reading is kept as `flow_scout`.
Nothing here reads a file name.

| ID | Status | Rule |
|---|---|---|
| FLOW-1 | in force | **The user's words win.** Words that state where the fluid goes ("flows through it", "internal flow", "pressure drop", "the fluid volume"; "around it", "external aero", "drag", "wind tunnel") decide, whatever the shape says, at 0.95; the shape's disagreement is kept as a reason. With no statement, the object the words name decides at 0.8 (a pipe, duct, manifold, valve, nozzle, artery: through it; a car, wing, aircraft, hull, building, propeller: around it). Words that state both, or take a statement back ("not internal"), decide nothing. The answer to FLOW-4's question is read the same way. |
| FLOW-2 | in force | **The measured shape decides only where it can tell.** From the measuring step's faces and the inside-space map (INS-1), each situation with the share it gets right on the labelled development corpus: the parts close off a space with openings where the measuring step reads flow through them (0.85, internal); several closed solids whose flat ends read as mouths (0.65, internal); open ends that lead into a way through it the map finds (0.9, internal); a closed solid shaped like a bent or branched passage, its flat ends the mouths (0.8, internal); a straight closed solid whose widest flat end is at least 0.8 of its cross-section (0.7, internal); many short holes through a thin plate, a perforated plate or a grille (INS-23; 0.7, internal, the stage asks); blades round a hub (0.75), a closed solid with no passage mouths (0.8; 0.7 when it has flat ends that do not read as mouths), a scene of many pieces (0.7), surfaces with no openings and no inside (0.65): external. Two flat ends are "straight" when they face apart and their centres lie off each other's axis by under a quarter of the wider one. **Undecided** (under 0.6): a surface with nothing inside it (it encloses under 0.5% of its box, with open edges, or a flat patch); an open skin with open ends; faces that read a body where the map finds a way through; ring ends with no way through; a straight convex bar; a straight solid that bulges past its two flat ends. |
| FLOW-3 | in force | **The pictures decide only where clearly surer.** The picture model's kind replaces the measured one only when it is surer by 0.15 (and at least 0.6), and never when it contradicts what was measured: flow through a part needs two openings and, for a wall, a way through the map finds; flow around never fits a part the map shows a way through. The user's words are never overruled by the pictures. |
| FLOW-4 | in force | **Undecided is said, never guessed silently.** A part no rule above decides carries `kind` "undecided", its best guess as `flow` (what the stage draws), and the one fixed question "Is the flow through the inside or around the outside?" for the intake to ask once. It is asked only once the naming has landed (the verdict then carries the user's first words and the pictures), beside the open stage, with two buttons, and never when `by` is "words" (`agents/intake/flow.flow_kind_question_due`, asked by the stage's read of the check). The user's answer decides by FLOW-1 and sets the stage's "The fluid flows" and "The file is" before Proceed; so does a flow the user states in the chat at any point before Proceed - the latest statement wins over the stored verdict (`agents/intake/flow.stated_flow_kind`). |
| FLOW-5 | in force | **A file that declares its regions decides itself.** A thermal model (ECXML) names its parts and the air among them: internal, at 0.95, whatever else is said. |
| FLOW-6 | in force | **First what the part is** (`application/part_understanding.understand`; the proposal's and the stored facts' `understanding`: object in plain words, class, mode, confidence, by, reasons, measured). The user's words name it first (0.9: "exhaust manifold" is a collecting manifold, "intake manifold" a distributing one, "mixing tee" mixes, "dividing tee" splits); the measured openings give the class from general geometry - two equal ends on one line (straight), with a waist (venturi), unequal on one line (reducer; a diffuser where the whole-shape reading names its narrow end), at an angle (bend), side by side facing one way (return bend), facing apart off one line (offset duct), a passage that opens into a chamber behind its ends (chamber: a valve body, a housing, a plenum), an eye on the part's axis with an outlet off to the side and tangential to it (volute), a run with a branch square to it (tee) or at an angle (wye), a stem with two equal arms (wye), a run or one larger opening with smaller branches (manifold), two or more separate passages (circuits), else a branching part - and say so when they disagree with the words, which win. The picture model's name is used only where the words name nothing (agreeing raises the sureness; it names the part alone only when the measured class is under 0.6). |
| FLOW-7 | in force | **Then which opening is which** (`part_understanding.assign`; each opening's `role_reason`: confidence, reason, guess). Sure only where engineering says: a pump or fan draws in at its eye (0.75), a diffuser is fed at its narrow end (0.75), a collecting manifold takes in at its runners and a distributing one at its larger opening (0.85, from the words), a mixing wye joins its arms into its stem and a dividing one splits from it (0.8, from the words). Everywhere else - two ends alike, a reducer, a tee that may split or mix, a manifold no words name - the measuring step's order stands and is marked a guess (0.4 to 0.55), which the stage shows as "a guess - check it" for the user to confirm or flip. The pictures may change a role only where they are surer than this; a role they set stays marked a guess. An opening the file declares is never reassigned. |
| FLOW-8 | in force | **A sticker means an opening.** The pictures carry stickers only on proposed openings, numbered with the stage's own ids; a face proposed as not an opening (a side pocket's mouth, a step in the bore) wears none. An undecided part (FLOW-4) is pictured with its openings stickered, so the pictures can help decide. |
| FLOW-9 | in force | **A body the map finds a way through is asked as flow through it, with the way's mouths** (`application/flow_kind._decide`, `THROUGH_CASE`; `application/geometry_check.through_part_openings`, `_is_mouth`; the holes' `passage_mouths`). A part whose faces read as a body in a flow while its inside-space map (INS-1) finds a passage with two mouths or more (FLOW-2's "faces that read a body where the map finds a way through") stays undecided and is still asked FLOW-4's one question with its two buttons, but its best guess - what the stage draws until the user answers - is flow through it (before: the faces' "flow around it"), its input kind a wall round a passage. Its openings are the mouths of those passages, each the flat face's hole of its bore measured exactly (INS-13), else the mouth as the map reads it on the drawn skin: a face-read opening that is a mouth (a hole, not a flat end's disc of metal; its centre within half the wider one's width of the mouth's, facing the same way within a dot of 0.9, its size within 1.25x) stays as read; a flat end's disc of metal (an end plug's 54 mm end faces round its 16 mm bore) and the mouth of a blind side pocket of the map (a bolt hole) are kept as not openings for the stage's click; any other hole the faces read stays proposed after the mouths (the map may not see it: a branch it reads with one mouth); openings that already are the mouths are left as they are. A body with no way through (blind holes only, one mouth) and every part another FLOW-2 case decides are read as before. The answer decides by FLOW-1 either way. Measured: built parts - a 56 mm plug with a 16 mm bore (asked, flow through it, the bore's two 16 mm holes; the end discs not openings), a block with a bore turning a corner (asked, flow through it, its two 12 mm mouths unchanged), a block with two blind holes and a block with one deep pocket (flow around it, decided, as before). The check step on the lab's 222 parts (STEP and triangle files, flow and not-flow; 824637a0 against this rule): 38 proposals changed, all by this rule, none otherwise; on 32 only the drawn guess changed (flow around it to flow through it, still asked), on 6 the openings too - two end plugs (their 54-60 mm end discs set aside for the 16 mm bore's two holes, and six small bores), a honeycomb plate and a cell end plate (end discs set aside for the mouths the map finds), an end cap (11 blind bolt holes set aside), an elbow of three solids (its two 47.6 mm ends added beside two 5 mm holes) and a chip plate (11 more mouths). On the eye-labelled parts: of 13 flow parts proposed as flow around it before, 11 are now guessed flow through it (the 2 left: a cooling plate the map finds no way through, a mis-scaled aorta); of 25 not-flow parts proposed as flow around it, 5 are now guessed flow through it (a sieve end cap, a lid, a chip holder, a stabiliser plate, a discharge ring): all are asked, the answer decides. The first pass of this rule also set aside every face-read hole the map did not read as a through mouth (a manifold's two side ports, a plate's 9.6 / 7.2 / 4.6 / 3.4 mm holes); hence only discs and blind holes are set aside. |

## PLAN-fea: the FEA meshing plan

A structural solid (purpose Structural / FEA, 3D, no face named by the user) is meshed by the
deterministic FEA driver (`engines/fea_*.py`), not the builder loop. The plan is computed from the part's
measurements (FEA build step 3: walls, hot spots, bodies) and is the same for every engine; each
engine is one adapter that meshes it (gmsh first, `engines/gmsh/fea_adapter.py`). The plan is
written to `fea_plan.json` beside the mesh, with these sentences in plain words. No model is asked
anything: AI changes to the plan are off (Areen's decision 4, 20 Oct).

| ID | Status | Rule |
|---|---|---|
| PLAN-fea-1 | in force | **Quadratic tetrahedra, solid only.** Version 1 meshes the solid with 10-node tetrahedra; thin walls are meshed as solid too (shells are version 1.1). |
| PLAN-fea-2 | retired | **The detail level set the element count** (Quick / Standard / Fine). Retired 21 Oct: one rules-based plan, sized by PLAN-fea-14 and held under the element limit by PLAN-fea-8. |
| PLAN-fea-3 | in force | **At least 2 elements through every wall.** Every face's measured wall gets elements of at most half its thickness, held through the wall. A part with a number of its own keeps its number. An area inside a part (NOTE-6) asked so ("make the mesh finer at the fillets") has each zone lying wholly on its faces at its OWN size halved (a round's, and a wall's through-thickness size - never the round's size over the wall's reach), plus a zone of its own at its finest size halved; "coarser" there keeps what the accuracy rules make finer; a zone only partly on a sized area keeps its own size (round 7: fea0254's 16 rounds, 289k planned elements, came to 1.9 million; holding the walls on them to the round's 0.028 mm made 124 million). The plan's words say it: "You asked for coarser elements on the frame: its own size is doubled, from 4 mm to 8 mm; walls, rounds and hot spots keep the sizes their accuracy needs." |
| PLAN-fea-13 | in force | **A progress watchdog, and a budget from the estimate.** A gmsh FEA pass runs until it is done or its budget (LAD-fea-15, rulebook 49) runs out. It is stopped earlier only when it has made no progress for the stall window (`gmsh_runner.FEA_STALL_WINDOW_S`, 900 s: no new mesher output, no new step in `fea_stage.json`, and no CPU burned or memory changed by the mesher's processes - `sandbox/liveness`; gmsh meshes a big assembly's curves for long stretches without printing a line, dev-areen 25 Oct), or at the hard ceiling of the machine it runs on - the Cloud Run mesh job's own limit (`MESH_TIMEOUT_SECONDS`, less a margin), or 20 hours on a VM (RUN-5) - and never at what the attempt or the pipeline has left: the pipeline's deadline moves on while the mesher shows progress (`application/pipeline_budget.progress_extension`: the deadline becomes the stall window plus two heartbeats after the last progress), so only a run with no progress for that long is ended by the clock (dev-areen 25 Oct: a pass still meshing was cut at 110 minutes and its retry given 1 minute). A driver's attempt is likewise judged by the pipeline's time, never the model loop's budget. The adapter notes each step (sizing, surfaces, volume, optimising, curving, writing) and re-notes its own Python steps every 30 s; the live line reads the step. The planned time (elements at the slow fill rate of the part's complexity class: simple 1,500, moderate 1,100, complex 1,000 elements a second) is kept in the why record for reference only, and no plan is cut down for time - only the job's memory lowers the element limit (PLAN-fea-16). A stop is told as ours (run_infrastructure) with what the watchdog saw: how long it ran, the longest silence, and whether it was stuck or hit the ceiling (`engines/gmsh/gmsh_runner._run_fea_watched`, `sandbox/safe_exec.run_watched`). Planning measures its size-field histogram on the job's cores (bit-identical to one core) and finds the first floor that fits by halving the list of floors (24 Oct: the 114-part caldera planned 14 histograms, 35 minutes). gmsh uses every core the job has for its own parallel work; the curves are meshed on one thread and the surfaces on every core by MESH-23 (gmsh's own threaded versions are not repeatable: lab, 24 Oct, 0 of 17 the same twice). |
| PLAN-fea-15 | in force | **The staged solid is read as gmsh's own B-rep.** The staging writes the metre-scaled solid twice: as STEP, and as gmsh's own B-rep file beside it (`geometry.brep`). The FEA path measures and meshes the B-rep when it is there: gmsh's STEP writer and reader together lose faces on some parts (an ANSI bolt could not be read back; an ISO 4762 screw left a face with no surface mesh). A solid the measurement still cannot read is healed (OpenCASCADE's ShapeFix) and measured again, with a note, so the part still gets a plan. |
| PLAN-fea-11 | in force | **Curving never makes an element worse.** An element that curving onto the CAD leaves under the quality floor and worse than its straight shape keeps straight sides (its midside nodes at the middle of its edges; `engines/gmsh/fea_settle.py`). **Settled to the end:** a straightened element straightens its neighbours on the edges they share, and a neighbour left half straight, half curved can fold, so the check runs again on the elements sharing a moved node until none is left under the floor and worse than straight (`fea_settle.MAX_ROUNDS` the backstop). dev-areen, 9 Nov: one round straightened 590 elements and left 4 of 6.47M inverted, and the whole mesh was refused; settled to the end, none. ox_mc_lid (lab, 27 Oct) the same: one round straightened 335 elements on two 2 mm plates and left 41 neighbours below zero; the rounds after it straighten them and leave none. |

The numbers are `engines/fea_plan.py` (the limit and the coarsening are `engines/fea_driver.choose_plan`). The estimate is read from the plan's own size field over the
part's volume (`engines/fea_size_field.py`), and the plan records it, so the plan can be worked out
again from what it recorded.

## LAD-fea: the FEA driver's fixed lever ladder

One attempt runs at most 3 passes. After a pass, the first trigger that holds pulls its lever, each
lever at most once. The passes do not use up the run's attempts.

| ID | Status | Rule |
|---|---|---|
| LAD-fea-1 | in force | **An invalid mesh** (a degenerate or inverted element): the next pass grows sizes more gently (1.2) and optimises three times instead of once. Elements under the quality note floor are a note, not a trigger. |
| LAD-fea-2 | in force | **No mesh came back** (the fill failed): the next pass fills with gmsh's other 3D algorithm first (Delaunay first, HXT after it; every pass fills with HXT first by MESH-25). |
| LAD-fea-3 | in force | **A plan rule fell short on the mesh** (through a wall, or round a hot spot): the zones that fell short are made 20% finer - never on a plan coarsened to fit the limit, which is short there by choice and says so. |
| LAD-fea-4 | in force | **More elements than the limit** after meshing (the estimate ran low): the next pass makes the finest zones coarser, aimed at 85% of the limit, never past what keeps elements valid. |
| LAD-fea-6 | in force | **No identical retry.** The surfaces a failed pass went wrong on - the ones the fill named, or the ones an invalid element touches - are meshed the other way (gmsh's MeshAdapt surface algorithm instead of the default) on the next pass - ONLY the surfaces that failed: a failure that names more than a quarter of the part's surfaces (a fill that names a whole volume's boundary) is not on those surfaces, and none is switched; and a large analytic face (plane, cylinder, cone, sphere or torus holding over 5% of the part's surface area) keeps the default, where MeshAdapt is very slow and gmsh switches by itself should the default fail there (shared dev, 1 Nov: all 441 faces of a 640 mm part put on MeshAdapt, which ground on its 180,000 mm2 cylinder for hours; rulebook 49): together with LAD-fea-1 or LAD-fea-2, or on its own when those were pulled already. A surface the default algorithm leaves with no mesh is meshed again with MeshAdapt at once, in the same pass. When there is no surface left to change, the ladder stops rather than run the same pass twice. An element the quality record reads as SICN 0.0 (under 5e-5, the record's four decimals) makes the pass invalid and is traced like an inverted one. **A sliver locked between two faces** (an invalid element whose four corners all lie on two surfaces, none inside: two faces facing each other across a wall one element thick get the same surface mesh, node across from node) names only the second face of the pair, so only that one is meshed the other way and the mirror breaks - every pair alike it (same kind and area, the same distance apart) names its second face too, so one pass breaks every mirror instead of one pane per pass; meshing both the other way mirrors them again (fc_glass_frames' 10 mm pane at 7.5 mm: worst SICN 1.5e-5 with both faces alike, 0.22 with one meshed by MeshAdapt). |
| LAD-fea-7 | in force | **Out of memory: the next machine, then no retry.** A pass killed for memory runs again unchanged one machine up (RUN-3) - no lever, no re-plan. Killed on the largest machine too, it pulls no lever (the other 3D algorithm and gentler growth need as much memory or more); the attempt ends saying the plan needs more memory than the largest machine has. |
| LAD-fea-8 | in force | **A surface stage that stalls is not run again the same way.** When the watchdog (PLAN-fea-13) stops the mesher while gmsh is still in its 2D stage, on surface N, the stall is the part's: gmsh threw away its Frontal-Delaunay mesh of a face because two triangles came out the same, and the MeshAdapt run it switched to can stay silent past the watchdog's window (nakuja_rocket's nose cone alone: 15 minutes on one face with a pole on a laptop-class worker). The next pass keeps gmsh's first mesh of every face (no switch to MeshAdapt), its repeated triangles dropped by MESH-5. The surface it stalled on is never put on MeshAdapt again by an earlier LAD-fea-6, and a pass stopped by its budget in the 2D stage (LAD-fea-15) pulls this lever the same way. **It also rides along after a failed pass in which gmsh switched a face to MeshAdapt by itself** (its default failed there and its switch-on-failure took over: a MeshAdapt line for a face first meshed another way, `fea_ladder.switched_surfaces`): the next pass's fill lever (LAD-fea-2 or -1) keeps gmsh's first mesh of every face, those faces are never put on MeshAdapt by LAD-fea-6, and its words say so - so the pass after a failure is not the same grind again (shared dev, 1 Nov: a face lying on another face spent 13 minutes in MeshAdapt on every pass, and the fill failed each time; rulebook 49). Once per attempt; any other guard trip stays ours and pulls no lever. |
| LAD-fea-9 | in force | **The last rung: fTetWild, only after every gmsh option** (`engines/fea_tetwild.py`). When every pass above - Delaunay, HXT, MeshAdapt on the surfaces that failed, and for an assembly the tie (PLAN-fea-17) - left no valid mesh, fTetWild (wildmeshing/fTetWild, pinned commit, MPL-2.0) meshes the part(s) still without one: an assembly's parts the failed passes named first, tied to the other parts' unchanged gmsh mesh; if that pass fails too, every part. Its ideal edge length is the part's base size and the plan's zones are its sizing field, its envelope a thousandth of the part's diagonal - each held to fTetWild's own sizes by LAD-fea-17; the CAD is tessellated within half the envelope; its time, stop and threads are LAD-fea-18's; the image's build is patched (seeds made constants, thread-stable, a stop file: `deploy/docker/ftetwild_patch.sh`), so the same input gives the same mesh. | LAD-fea-10 | in force | **The last rung's ideal edge is never longer than the part.** A plan coarsened to fit (PLAN-fea-8) floors every part's base at its zone floor, and on a big assembly that floor passes the small parts' own size (ox_mc_lid: 61 mm on parts of 3 to 20 mm). gmsh is held there by each part's face zones; fTetWild, asked for edges twenty times its part inside an envelope a thousandth of it, ran past 37 GB and an hour on a 3.2 mm part and past 41 GB and two hours on a 6 mm one without finishing. A part whose base is within its own size - every part of a plan not coarsened that far - is unchanged; the rung's settings say `edge_rule` and the plan's base where it held. |
| LAD-fea-11 | in force | **Parts a failed pass did mesh are kept; later passes mesh only the parts that failed.** Parts meshed apart (tied or contact) are filled one by one; the fill stops at the first part it fails on (after an error gmsh refuses every further mesh call in that process) and the pass keeps the parts it filled - a volume gmsh left empty, or filled with a flat or inverted element (SICN under 5e-5; kept, Netgen's optimiser crashed on one, the folding chair, lab 28 Oct), is a failed part, never a kept one (`fea_kept_parts.msh`: gmsh's own file at the scale the pass built at, with each node's place on its face; `fea_kept_parts.json`: the scale, the sidecar's ties, the kept and failed volumes). A new staging (the tie after a fused pass) starts afresh. ox_mc_lid: pass 1 fills 238 parts in about 5.5 h and stops on Part_239; pass 2 fills the 14 not reached and fails on Part_239 again (about 40 min instead of 5 h), and the rung's pass gives Part_239 alone to fTetWild. |
| LAD-fea-12 | in force | **The last rung's slivers on the surface are taken off, or set aside and named** (27 Oct, `engines/fea_tetwild.peel_flat`, `mesh_into`). fTetWild can leave all-but-flat tetrahedra on the part's surface: volume under 1e-6 of the longest edge cubed (a regular one has 0.118), SICN about 5e-5 and under - what the quality record (four decimals) reads as 0, so the ladder calls the pass invalid. Such a mesh is NEVER a clean pass: the concern row is always missed, so the verdict is "with concerns" (VER-2) - a bad element hidden from the user is worse than a failure. Validity still holds it (none may be inverted). A flat one wholly inside is left for the gate. ox_mc_lid (lab, 27 Oct): Part_239's 769,908 tetrahedra had nine such slivers in two spots 20-50 microns across - the flattest measured inside out by gmsh, alone failing the delivery; seven are dropped and two set aside. |

## RUN: where a mesh runs

A plan is sized by the accuracy rules alone, then sent where it fits (Areen, 24 Oct: a bigger machine
replaces shrinking a mesh to fit). Engine-neutral: any driver writes the decision into its workspace
(`contracts/mesh_machine.py`, `mesh_machine.json`) and the mesh executor runs it there
(`adapters/mesh_execution/cloud_run_client.py`, `gce_vm.py`).

| ID | Status | Rule |
|---|---|---|
| RUN-1 | in force | **Decided before meshing, from the memory model.** The mesher's peak (the engine's measured model, with its margin) plus the workspace's files (Cloud Run keeps them in memory: about 2,300 bytes an FEA element) is held against the Cloud Run mesh job (32 GiB, 90% usable). It fits: Cloud Run. It does not: the smallest Compute Engine VM whose memory holds the mesher alone (a VM's workspace is on disk) - n2-highmem-8 (64 GB), -16 (128), -32 (256), -64 (512), m1-ultramem-40 (961). ## The FEA builder's AI decisions (AI-fea-n): AI governs, rules guarantee

The builder model (the builder route) is shown the part as measured and the user's own words, and
answers ONE `fea_decision` tool call against a strict schema: no mesher command, no size. The rules
below turn each choice into exact sizes. The round goes through the AI decision cache, so the same
part with the same words gets the same decision and the same mesh. `FEA_AI=off` gives the rules'
own plan.

| ID | Status | Rule |
|---|---|---|
| AI-fea-1 | in force | **Refine** (the stress there matters to this user or this analysis): a hole, fillet or notch gets 10 elements per quarter-turn and 4 through the wall beside it; a wall 3 through it; a round 6 per quarter-turn (as a hot spot). Never finer than half the size the zone's own rule asks for; a sharp corner is never refined past its cap (its stress never settles). |
| AI-fea-2 | in force | **Coarser** (it does not matter for this analysis): a hole, fillet or notch keeps only its shape - 4 elements per quarter-turn and 2 through the wall, as any round (PLAN-fea-7); a sharp inside corner is capped at half its wall instead of a quarter. Walls and rounds are at their minimum already and stay. |
| AI-fea-3 | in force | **Small features.** Set aside: a hole, fillet or notch of radius at most 2% of the part's diagonal is meshed as coarser (AI-fea-2); a wall or anything larger is never set aside. Keep: a micro detail (PLAN-fea-12) at least a fiftieth of the base size gets a zone of its own size, so the mesh follows it; a smaller one stays set aside. |
| AI-fea-4 | in force | **An element count the user named is read by the AI** - only one they stated, in any words they wrote it (`1.2mil`, `half a million`, `700k-1.5M`, a count of nodes converted at about 1.5 nodes per 10-node element) - as `target_elements`, with `target_min` / `target_max` for a range or alone for a ceiling or a floor. ## MESH: a good file is never blocked by our own broken-CAD checks

Areen, 24 Oct: mesh first. A pre-mesh check that the CAD may be broken warns; only a mesh that then
fails at the flagged spot tells the user the part needs CAD repair. Detect only, never heal
(`cad/suspect_defects.py`, `application/fea_check.py`, `engines/fea_driver.py`).

| ID | Status | Rule |
|---|---|---|
| MESH-1 | in force | **Warn, then mesh.** Wherever a closed solid can be read (a CAD file with a solid body, or a triangle file whose surface closes), a face crossing another of its body, a paper-thin fold, and an open or invalid patch the clean check finds are WARNINGS on the stage, with the faces named - never a stop. The run meshes; a valid mesh is delivered with a note naming the spot. The only stops before meshing are a file nothing can be meshed from (a triangle surface that does not close, a CAD skin that nearly closes but for a gap, or nothing) and an unreadable file; a CAD file that is a surface is meshed as a shell (SURF-1, rulebook 59). A defect is CONFIRMED only when two independent measures agree (the fold's gap test or the crossing search, and OpenCASCADE's Boolean self-interference check on that solid alone naming the same faces); anything less is a note. **The checks are time-boxed** (rulebook 72, `cad/suspect_defects.find_bounded`): each runs in a child process under its own limit - the crossing search 300 s, each solid's Boolean check 60 s and 0.2 s a face of that solid, at most 300 s; no Boolean check of a solid no suspect lies on starts past 60 s - and a check past its limit is stopped and said as not checked (the run's note and its decision record), never a wait: a turbocharger's run spent minutes of "Measuring your part" in them, unbounded (17 Nov). The run shows them as their own step ("Checking for defects"). |
| MESH-2 | in force | **Needs CAD repair only where the mesh failed.** When every pass fails and the faces the mesher failed on (gmsh's own error, or the invalid elements) are faces a check flagged, the user is told the part needs CAD repair, with those faces named; the run is not taken again. A failure anywhere else is the ordinary FEA outcome. |
| MESH-3 | in force | **Zero false stops, gated.** Every broken-CAD check runs over the known-good files (`devtools/quality/broken_cad_gate.py`): CI holds the fixture set to zero stops on every change, and any change to a check runs the whole corpus (the clean CFD corpus's gate tier, the FEA corpus dev and holdout - presence and verdict only - Areen's files and the assembly corpus A set) on a lab VM, which must show zero stops. |
| MESH-4 | in force | **Meshed at the CAD's own scale when metres fail.** The staged solid is in metres, so OpenCASCADE's fixed tolerances (1e-7 of a model unit) are a tenth of a micron: a CAD edge of a few nanometres where one feature grazes another (libredrive_pulley_housing: a 1.8 mm half-hole touching a 28 mm bore, edges of 24 nm, 56 um and 24 nm) falls inside them, and gmsh stops ("Impossible to mesh periodic surface", "overlapping facets", a volume left empty). ## AIG: the AI never fails or retries a run

The rules plan comes first. An AI change is used only when it is valid and inside the rules' bounds,
and every AI error falls back to the rules. These rules cover the AI steps outside the FEA builder
(AI-fea-n above) and the verdict (VER-5).

| ID | Status | Rule |
|---|---|---|
| AIG-1 | in force | **The rules build when the AI builder gives no mesh.** On cfMesh, VMTK, gmsh (CFD) and snappy multi-region, an attempt whose builder model was down, busy, slow, raised, or ended its rounds without submitting a mesh is built in the same attempt by the rules plan (`engines/rules_plan.py`): the same tools, validation and gates, the layer count the request names, every size from the engine's own defaults. It is never an infrastructure retry and never a failed run. The why record and the run's notes say so. `BUILDER_AI=off` builds every such attempt by the rules plan. |
| AIG-2 | in force | **The AI plan is never worse than the rules plan.** Before an AI builder plan is used, its planned cells (the engine's own estimate of the case configure_mesh just wrote, at the sizes the mesher really makes) are checked against the one-job cell limit. When the AI plan is over the limit and the rules plan (`engines/rules_plan.py`) is not, the rules plan is configured instead (`engines/plan_guard.py`), the builder's tool result says so in plain words with both numbers, and the why record cites this rule. An estimate that cannot be read, an engine with no rules arguments to compare, or a rules plan that fails or is no better leaves the validated AI plan in force. cfMesh carries an estimate; VMTK fits every strategy to the limit itself, the snappy planner holds max_cells to it and the FEA AI is bounded by AI-fea-5. |
| AIG-4 | in force | **An attempt the engine handed on is not built again by the rules plan** (rulebook 77; `agents/builder/invoke._handed_on`, `HANDED_ON_RULE`). AIG-1's rules plan builds an attempt the AI gave no mesh for; but when run_mesh itself ended the AI's turn (tools/meshing HANDS_OFF: no mesh, and none this engine makes of this case with this plan) the rules plan ran the same plan into the same failure (abc 63401: a second 4.5 minute run for the same zero-face outlet_3).
