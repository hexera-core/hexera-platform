CAD repair research artifact

CAD repair has to become a service workflow that fixes geometry, meshes it, and proves the result.

This map turns the current repair draft and diagnostics slice into an implementation-oriented service plan. The goal is not inspection for its own sake; it is a repeatable operator workflow that gets customer CAD repaired, meshed, validated, and delivered.

Operating model

The company should run CAD repair as a service operation with software-enforced evidence. The customer submits geometry and desired mesh intent; the internal system creates a repair job, routes it through automated and operator steps, generates a mesh, and delivers a bundle that explains what changed and why it is acceptable.

The current diagnostics-only package under meshpipeline.cad.repair is the intake instrument. It should become the first state in a repair-to-mesh job, not a terminal product.

Service promise

Return one of three outcomes: delivered mesh, delivered repair-only artifact with explanation, or blocked job with a precise customer/operator action.

Primary workflow

Upload, interpret units, inspect defects, choose strategy, repair, validate, stage, mesh, review, package, and deliver.

Operator role

Operators handle exceptions, approve risky repairs, run manual CAD cleanup when needed, and annotate decisions that can train later automation.

Automation role

Deterministic tools perform geometry changes and meshing. AI routes work, drafts repair plans, explains evidence, and learns from operator decisions.

Definition of done

A job is done only when the customer can download the mesh bundle or when the operator has sent a precise blocker with supporting evidence.

Evidence bundle

Original source identity, unit basis, defect report, repair plan, changed artifact identity, after-checks, mesh quality summary, and operator notes.

First commercial slice

Internal operator queue plus conservative automatic repair for STEP/IGES, followed by existing engine staging and mesh execution.

Repair-to-mesh service phases

Each phase should move a customer job toward delivery. If a phase cannot advance automatically, it should create a precise operator task rather than leaving the job as a vague failure.

1

Identity and interpretation

Freeze source id, hash, suffix, size, unit basis, and materialized path before repair sees the file.

implemented basisAI can explain unit risk
  • Never infer units inside repair.
  • Repair output becomes a new source only by explicit product action.
2

Format-specific inspection

Run B-rep inspection for STEP/IGES and triangle-surface inspection for STL/VTP. Keep the taxonomy stable so operators see the same defect language across jobs.

slice 1 existsAI triage labels
  • B-rep: validity, entity counts, invalid/no-face outcomes.
  • Surface: duplicate, degenerate, boundary, and non-manifold metrics.
3

Failure localization

Attach defect locations, affected entities, screenshots, and small repro extracts so operators know what to fix and what to ignore.

AI-native evidence clustering
  • Cluster repeated defects by region and entity type.
  • Generate concise repair rationale from structured facts.
4

Repair strategy selection

Choose conservative, mesh-ready, or manual-review strategy from measured defects, model scale, engine target, service SLA, and user intent.

AI-native classifier
  • AI recommends the job path; deterministic gates enforce caps.
  • Create an operator task when deletion or defeaturing could alter design intent.
5

Conservative kernel repair

Use bounded OpenCASCADE operations for B-rep wire/order/gap/tolerance/sewing fixes. Save repaired output separately and reject over-cap deviation.

geometry mutation
  • No feature deletion in the first automatic repair mode.
  • Record geometry, topology, and tolerance deltas for operator/customer review.
6

Surface repair path

Use a service-gated triangle repair path for STL/VTP jobs where CAD-source repair is unavailable. Treat CGAL-style repair as the reference behavior while packaging is decided.

dependency decisionrepair recipe ranking
  • Candidate operations: orient, stitch, remove duplicates, fill holes, split intersections.
  • Keep exactness and snap-rounding behavior visible in reports.
7

After-check and engine admission

Re-run validity, deviation, region preservation, staging, and engine admission against the effective geometry before spending mesh time.

engine gates already existfailure prediction
  • A green repair is not enough; downstream staging must improve.
  • AI can predict likely engine success before expensive runs.
8

Mesh, review, and deliver

Run the selected meshing engine, review mesh quality, package repaired geometry and mesh artifacts, and produce customer-facing evidence.

core mesh pipeline existsreview summarization
  • Delivery is the acceptance state, not "repair attempted".
  • Operator review should focus on exceptions, quality failures, and customer-risk decisions.

How it connects to the existing mesher

CAD repair should not become a second pipeline. It should become the missing geometry-preparation layer between verified execution geometry and the existing engine admission/build/review loop. The current mesher already has the right seams: deterministic engine selection, metre-normalized staging, engine-owned admission, Cloud Run mesh execution, artifact delivery, and final-result truth.

State contract additions

Do not add effective_geometry casually. The current state contract has one authoritative geometry. First implementation should either replace geometry only after approval and record lineage, or explicitly update every consumer to choose an effective geometry handle.

Graph insertion

Insert repair inspect/strategy after materialized geometry and before geometry admission. Repair mutation can remain disabled until later slices; dispute and first-review bypass routes must keep their current short-circuit behavior.

System design

The plan needs one shared repair service, not separate implementations for product, operator tooling, and meshing. Every caller should create or attach to the same repair job and read the same evidence model.

Repair job service

Owns job state, source identity, strategy, attempts, operator tasks, artifacts, status transitions, and customer-visible summaries.

Repair executor

Runs inspect, OpenCASCADE repair, surface repair, deviation checks, and after-checks. It never overwrites source geometry.

Meshing handoff

Receives only validated effective geometry. If repair output fails staging, the system returns to repair review instead of burning mesh capacity.

Operator console

Shows queue priority, defect evidence, suggested strategy, repair attempts, before/after checks, mesh quality, and delivery actions.

Delivery packager

Builds a final bundle: repaired CAD when present, mesh artifacts, repair report, mesh quality report, screenshots, and operator notes.

AI assistant

Produces recommendations and summaries, but all state transitions that mutate geometry or deliver output require deterministic evidence.

Bad CAD

The geometry is objectively defective or not safely repairable. The customer-facing result says what to change or what service path remains.

Service failure

Storage, kernel, queue, worker, or mesh infrastructure failed. Do not describe this as the customer's geometry problem.

Engineering judgment

The geometry can be changed, but the change may alter intent. Assign an operator task and record the decision, not an automatic fix.

AI-native service surfaces worth building

AI-native here means a workflow that learns from geometry, repair outcomes, operator choices, mesh quality, and delivery results while deterministic components perform exact geometry mutation and meshing.

Job triage classifier

Inputs: repair report, scout metrics, engine target, user intent, SLA, historical repair outcomes.

  • Predict auto-fix, operator-fix, remesh-only, or request-new-CAD.
  • Rank defect families by likely meshing impact.

Repair-and-mesh planner

Inputs: defect clusters, model scale, tolerance cap, target engine, available kernel operations, and mesh quality target.

  • Propose a bounded operation sequence and engine path.
  • Emit a plan that can be replayed deterministically.

Delivery narrator

Inputs: before/after measurements, changed topology, preserved named regions, staging result.

  • Explain what changed, what was meshed, and what remains risky.
  • Make downloadable reports useful to customers and operators.

Workflow learner

Inputs: repair job corpus, user approvals, engine failures, final mesh quality, operator overrides.

  • Improve policy defaults by geometry family.
  • Detect when a model should skip repair and ask for CAD-side redesign.
Boundary: AI can drive the service workflow, but customer-deliverable geometry and meshes must come from deterministic executors with tolerance caps, source identity, before/after validation, and mesh-quality evidence.

Why this is AI-native

The system is organized around a learning loop: perceive geometry, plan bounded actions, execute exact tools, critique downstream results, and feed outcomes back into routing.

Why this is not an AI CAD editor

AI never owns geometry truth. It manipulates plans, labels, summaries, and recommendations. Exact repair and meshing remain replayable tool executions.

Promotion ladder

Shadow recommendations, operator-visible suggestions, one-click operator approval, policy-controlled auto-route, then auto-execute only for fixtures/corpus classes with passing regressions.

Promotion gate Required evidence Blocker Rollback trigger
Shadow to visible suggestion Fixed corpus shows recommendation agreement with operator route above the selected threshold, with calibrated confidence and abstentions. High-confidence wrong route on any must-block fixture. Operator rejection rate rises above baseline for the same defect family.
Visible suggestion to one-click approval Delivery-rate improvement without mesh-quality regression, geometry-deviation regression, or increase in manual cleanup time. Suggested route hides a declared engine mismatch as a geometry repair. Customer blocker, reopened job, or peer review finds misleading rationale.

False auto-repair above the agreed ceiling or confidence not monotonic with success. Any delivery dispute caused by AI route choice disables that policy version.

Any design-intent operation: deletion, defeaturing, region loss, large tolerance inflation. Any over-cap mutation, mesh-quality regression, or missing lineage artifact.

The fastest path to revenue is an internal service console, not a polished self-serve repair product. Build the narrow repair-to-mesh loop first, then automate the operator decisions that repeat.

Research readout

The latest direction is not "AI replaces meshing." It is measured automation around geometry preparation: classify the part, localize defects, choose decomposition/defeaturing/repair actions, predict mesh failure, run exact tools, and prove downstream improvement. The service plan should follow that pattern.

Recommended direction

Build the repair system as a service operating loop. Every job should move from intake to repair strategy, repaired artifact, mesh attempt, mesh review, and customer delivery evidence.

  • Ship pipeline inspect next because every service job needs a defect baseline.
  • Add durable repair jobs and an operator queue before standalone self-serve polish.
  • Turn on conservative repair as soon as after-checks, region preservation, and deviation caps exist.
  • Use AI first where it increases throughput: triage, strategy recommendation, operator notes, mesh-failure prediction, and delivery summaries.
The acceptance test is a delivered service result: repaired geometry plus a mesh that passes staging, quality review, and customer-facing provenance.
