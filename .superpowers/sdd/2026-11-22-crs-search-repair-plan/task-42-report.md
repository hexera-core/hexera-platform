## Item 1: what I found and did
**Diagnosis (before coding).** The box with a deleted face yields `S@open`, `S@invalid`, `S@unlocated`. The open site comes from layer 1's `open_shell` finding, which names a SHELL (`H1`) that has no stable id, so the site is whole-part with `entities == []`. `fill_loop` takes edges, so there was nothing to target. Confirmed in a trace: the det sweep proposed `sew`, `make_volume`, `orient_and_close` only.

**Edges onto the open site.** New kernel function `sites_free_loops` (`sites_kernel.py`): edges bordering exactly one face (non-degenerate), joined with `ShapeAnalysis_FreeBounds.ConnectEdgesToWires_s` the way the op does, closed wires only, each returned as kernel edge indices plus the loop's bbox diagonal. `sites._attach_free_loops` translates indices to stable ids and puts them on `site.graph["free_loops"]` (smallest first, cap 6) with `diagonal_mm`, on every `open` site, after the graph is built. It is deliberately NOT put in `site.entities`, so site ids, anchors and the registry are unchanged. It is also shown to the model in the observation. One kernel call per search state with an open site; a failed call leaves `free_loops == []`.

**The sweep.** `DetGenerator._fill_rows`: one `fill_loop(edges, continuity="G0")` per carried loop that passes `limits.fill_span_allowed(span, diagonal)`; a loop over the cap is not proposed and is noted. G0 only because a planar fill ignores G1 and the op reports what it achieved. The cap is the existing `limits` function, no new constant. An unbounded part (Task 41's `UNBOUNDED_DIAGONAL_MM`) gets no `fill_loop` and says why via `_why_no_size`. The loops cannot be scaled any more than "within the cap", so there is no new absolute-mm parameter.

**The second op needed a second change (finding).** After `fill_loop` the shell is closed, layer 1 no longer says open, it says `no_solids`, which maps to an `invalid` whole-part site, and `make_volume` was only proposed for `open`. So fill-then-volume was unreachable even with `fill_loop` proposed (trace: search stopped `exhausted` after S1 with only `orient_and_close` duplicates). Fix: whole-part sites record the layer-1 code(s) that made them (`graph["hard_codes"]`), and the sweep proposes `make_volume` on an `invalid` site carrying `no_solids`. `make_volume` declines (never fails) when the faces enclose nothing. No change to layer 1 (Task 41's files untouched except for the merge).

**Budget finding (separate from the ops).** At default `patience=3`, `k_propose=12`, `ops=12` the search reaches the two-op solution: S0 (fill_loop child S1, plateau: score equal to parent) -> S1 (make_volume child S2, clean). Trace: 8 ops spent, 5 verdict candidates, stop reason `clean`. The plateau step costs one unit of patience, so the budget supports ONE plateau step before the solution. A part with several holes needs one plateau step per fill (each round without improvement counts against patience 3), so a 3+ hole part would stop on `patience` before the volume is built. Not tuned; not hit by the fixable case.

## Item 2: the injector's deviation test
`face_delete` now selects a face only if (a) its loop is within the cap (`limits.fill_span_allowed`, unchanged) AND (b) the op's own fill accepts it. (b) is MEASURED, not a proxy: `_fill_restores` writes the damaged part to BREP, re-reads it (so edge indices are the file's), collects the free edges and calls the registered kernel function `ops.faces._fill_loop` with continuity G0. Accepted means the op's span cap, single closed loop rule and fill-to-surroundings deviation against the fidelity bound (0.1 mm) all pass. There is no proxy error to bound. The one difference from the real run is that the part is measured as in-memory-written BREP rather than after the STEP round trip; STEP prints ~1e-6 mm, so a case is misclassified only if its deviation is within ~1e-5 mm of the bound, and the label records the measured number (`fill_fill_to_surroundings`, `fill_bound_mm`, `fill_fill_surface`) so such a case is visible. The `fill_loop` deviation bound was not widened.

**What moved into the declined stratum.** New sibling kind `face_delete_inclined` (status `declined_stratum`, `expected_outcome: correctly_declined`, opt-in via `ADMITTED_KINDS`, not in `DEFAULT_KINDS`): a face whose loop is within the cap but whose fill the op declines. The reason differs from `face_delete_large` (too large), so it has its own kind and the label carries `fill_loop_declined` with the op's reason. Report/reprobe/pool machinery needed no change (it keys on status). On a part with a 3 mm corner chamfer the chamfer face (loop 4.2% of diagonal) is declined `over_bound` (about 1 mm against 0.1 mm); ordinary flush patches are accepted.

**Regeneration, plainly: selection changed AGAIN.** `inject.py`'s revision hash changes and `face_delete`'s seed-to-face mapping changes for any part that has a small face the op declines (for parts whose small faces are all fillable the candidate list is unchanged, so seeds map as after Task 39). Existing recipes that include `face_delete` already read as a revision mismatch from Task 39; they still need regenerating, once, from this revision.
